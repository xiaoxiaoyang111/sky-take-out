# 部署、初始化与回退

本文件交付部署配置与操作步骤，不代表已经公网部署。当前没有云服务器、域名、证书或手机真机验收记录；不自动购买资源，不把本机地址写成在线演示地址。

## 环境与首次准备

- Linux服务器、JDK17、MySQL8、Redis、Nginx；创建独立数据库与受限应用账号，不复用历史开发数据库密码。
- 后端只监听服务器127.0.0.1，由Nginx提供HTTPS。MySQL/Redis端口不对公网开放。若数据库跨主机，连接URL应按实际证书配置TLS，不能照搬示例中的本机非TLS连接。
- 创建服务账户`rental`，应用目录`/opt/longyuan-rental`和可写持久目录`/var/lib/longyuan-rental/uploads`。数据库、Redis和上传文件都要备份。
- 复制`deploy/rental.env.example`至`/etc/longyuan-rental.env`，填写真实配置并设置仅管理员可读（600）。签名密钥使用两个不同的随机值，各至少32字符。prod配置会拒绝短值、示例值和开发fallback。
- 实际部署仅启用`prod`（需要模型再设置对应变量），不能同时启用`dev`，否则可能导入本机配置。模型代理通常留空，由服务器自己连接DeepSeek。

## 构建与数据表

1. `mvn -Dmaven.compiler.release=8 package`，以及前端`npm ci && npm test && npm run build`。
2. 上传后端JAR为`/opt/longyuan-rental/rental.jar`，前端dist内容放入`/opt/longyuan-rental/web`。
3. 按顺序执行：`000-employee.sql`、`001-schema.sql`、`001b-order-index.sql`、`003-member-center.sql`、`004-customer-avatar.sql`。`002-demo-catalog.sql`仅演示库按需导入，正式库不导入。`database/testing/legacy-schema.sql`是CI专用，不部署到正式库。
4. 初始化连接使用专门迁移账号。应用运行账号只授予所需数据库权限；密码通过受限客户端配置文件或环境传递，不放在命令参数中。

## 首个管理员

租赁端没有公开管理员注册接口。使用受控的一次性启动创建新管理员：

1. 在安全的服务器shell中加载prod环境，并设置`RENTAL_BOOTSTRAP_USERNAME`、`RENTAL_BOOTSTRAP_PASSWORD`。密码至少12字符且最多72个UTF-8字节，不要发到聊天或写到仓库。
2. 执行`java -jar rental.jar --spring.profiles.active=prod,bootstrap --server.port=0`。
3. 看到管理员创建成功后应用会自动关闭；清除bootstrap用户名/密码，常规服务仅启用prod。已有同名员工时拒绝覆盖，不会重置密码。
4. 新员工密码以BCrypt保存，仅租赁员工登录接口支持该新格式；旧外卖员工MD5登录保留兼容。不要用旧外卖登录页登录新建的BCrypt员工。

## 启动与验收

- 安装`deploy/longyuan-rental.service`，检查路径和用户权限，再由systemd启动。日志从journal读取；启动失败先检查必需环境变量、依赖连通性和上传目录权限。
- 按`deploy/nginx-production.conf.example`替换域名、证书与站点路径，`nginx -t`通过后再reload。现有站点保持独立，不覆盖原站点配置。
- 从公网确认首页、`/me/profile`深链、图片、登录、报价、预约及员工履约。404刷新、3MB反向代理上传上限、用户角色隔离、模型超时都要核验。
- TLS证书与域名接入按服务器实际情况办理。未完成公网验收前，简历只写“提供部署配置”，不写“已上线”。

## 模型运行边界

- Key仅在服务器环境中保存；客户不需要Key或代理。默认不开启模型，配置后先做真实咨询验收。
- 不限制客户每天或每分钟的咨询次数；同用户一个在途请求，模型客户端默认最多4个同时生成请求/实例，避免瞬时耗尽后端线程。该机制不是费用预算控制，也不是跨实例全局限流。
- 自由问题只发送公开目录和规则；本人订单由服务端直接查询。超时/失败不自动重试付费调用。
- 公网开放前，运营者还应在供应商账户设置适合的费用告警或可用预算；项目目前没有跨用户的账单统计与自动停机系统。

## 备份、升级与回退

1. 升级前备份数据库及上传目录，保存当前JAR、dist、配置版本和备份校验值。SQL迁移必须先在隔离库验证。
2. 上传新产物后切换版本并重启，验证注册/登录、目录、报价、订单和模型。失败则切回旧JAR/dist。
3. 本轮迁移为新增表，旧代码可以忽略；不要为回退删除新表或清空用户数据。若未来迁移修改已有列，应另写兼容方案。
4. 备份恢复演练应使用隔离库和独立上传目录，验证订单、头像和图片对应关系；当前尚未在云环境执行恢复演练。

历史Git曾包含开发数据库配置。本轮只移除当前版本明文，不重写用户要求保留的历史；正式部署必须使用全新凭据，历史上暴露且仍有效的凭据需由持有者轮换。
