# 有限规模性能与并发验证 · 2026-11-03

这些数据来自本机开发环境，不是生产承载量，不是优化前后对照。不能把本机短时吞吐直接写成“系统线上QPS”，也不能据此填写性能提升百分比。

## 环境与路径

Windows 11，AMD Ryzen 7 7840H（16逻辑处理器），Node.js v24.18.0客户端；同机Nginx → Spring Boot/JDK17 → Redis/MySQL。接口为公开目录`GET /rental/equipment?page=1&pageSize=12`，数据库中是少量演示器材，没有真实用户网络延迟。

## 只读目录样本

执行`node scripts/Benchmark-Rental.mjs`，预热20次，并发8。程序在10秒或10000次请求中先到的条件停止；此次先达到10000次请求上限，用时6.034秒。

- 请求数10000，错误0。
- 客户端P50：4.41ms；P95：7.79ms；P99：10.02ms；最大22.04ms。
- 此窗口内观测吞吐1657.14次/秒，仅代表本机已热身目录读取样本。
- 不包含预约写入、图片上传、模型生成、冷缓存或长时稳定性；没有证明CPU、数据库或网络上限。

原始机器可读数据：[benchmark-report.json](evidence/2026-11-03-benchmark.json)。脚本只允许回环地址，避免误对公网压测。默认无写入，也不会调用付费模型。

## 实物分配正确性

`node scripts/Verify-Rental.mjs`创建一个独立测试型号及一件READY实物，同一租期同时发送20个不同requestId的预约请求。结果：1单成功，19次业务拒绝；数据库确认仅一笔待确认占用，随后取消并清理全部测试记录。

此项证明该受控场景下未超订，属于并发正确性验证，不是吞吐性能结论。Junit中另覆盖相同requestId并发重试、相邻租期、取消释放、逾期未归还与事件插入失败回滚。
